## Code Canonicality

Same logic must have exactly one implementation in the repo. Version evolution belongs in git history, not in filenames or identifiers.

- Before adding any function, class, module, or file: grep the codebase for existing similar implementations. If found, extend or refactor the existing one. Only create new if truly absent.
- Forbidden suffixes for filenames, class names, function names, and module names: `_v1`, `_v2`, `_v3`, `_new`, `_old`, `_backup`, `_temp`, `_copy`, `_final`, `_real`, `_improved`, `_refactored`, `_fixed`, `_legacy`, `_deprecated`. If one exists in the codebase already, treat it as debt to unify, not a pattern to extend.
- Refactor in place: commit the working state first, modify the original file, run tests. If it breaks, `git revert`. Never keep an old version alongside the new "just in case" — git is the safety net.
- No parallel implementations as a transition; replace atomically.
- Commented-out code is debt, not a safety net. Delete it; git remembers.
- Unreferenced functions and dead code paths are debt. Wire them up in the same change or delete them.
- Do not use the repo as a scratchpad. Directories like `tmp/`, `scratch/`, `backup/`, `_old/`, `deprecated/`, `archive/`, `wip/` must not appear in commits.

## Project Identity

SHUD (Simulator for Hydrologic Unstructured Domains) is a multi-process, multi-scale hydrological model in which the major hydrological processes are fully coupled with the semi-discrete finite volume method on an unstructured triangular mesh.

- **Primary consumers**: hydrology researchers and watershed modellers; the rSHUD toolbox prepares inputs and reads outputs.
- **Lifecycle**: years (a research model maintained across papers; published results depend on it).
- **Team scale**: small team.
- **Strictness profile**: L3 (strict) — chosen explicitly at init; thresholds live in `constraints.yaml`. Re-run `eng-init` to change the profile; do not relax individual gates ad hoc.
- **AI tools targeting this repo**: Claude Code (`CLAUDE.md` imports this file).
- **Domain language**: `CONTEXT.md` is the bounded-context and invariant map; `openspec/glossary.md` is the canonical glossary. Check both before naming a domain concept or moving model logic.

## Conventions

### Naming

- Files and identifiers: follow the surrounding code (`MD_*.cpp` for `Model_Data` members, PascalCase classes, existing variable names from the papers).
- Tests: `tests/test_*.cpp` built by a `make` target; reference data under `tests/reference/`.
- Forbidden suffixes: see Code Canonicality.

### Debt markers and deviations

- `FIXME` — should block the next release. `TODO` — fix as soon as resources allow. `XXX` — maybe someday.
- Every non-default threshold, tolerance, exemption or compiler option carries a comment naming the failure it prevents.

### Tests accompany changes

A change under `src/` must change `tests/` (`make pr-gates`). Which evidence is required depends on the change (review-only; tick it in the PR template):

| Change | Required evidence |
|--------|-------------------|
| Bug fix | a test that fails before the fix and passes after |
| Conservation, numerical or solver change | an invariant test (identity, antisymmetry, pure right-hand side, unit invariance) |
| Physical closure change | invariant tests pass; `tests/reference/` updated with a before/after comparison and a record in `decisions/` |
| Refactor | `make regress` passes with `tests/reference/` unchanged |

### Reference results

- `tests/reference/` and `tests/io_contract/` are rewritten only with `make regress UPDATE=1` / `make test UPDATE=1`, locally; CI refuses `UPDATE=1`.
- Never update them or widen `regression.*` tolerances in `constraints.yaml` to make a gate pass. An update needs a physical reason in the PR and a record in `decisions/`.

### Commit format

- Conventional commits: `<type>(<scope>): <message>`; types `feat`, `fix`, `refactor`, `chore`, `docs`, `test`, `ci`, `build`, `perf`; scopes are free (`rhs`, `lake`, `river`, `et`, `build`, `omp`, ...).
- Enforced by `.githooks/commit-msg` and `make pr-gates` (which also checks the PR title, used for squash merges).

### Pull requests

- Use `.github/PULL_REQUEST_TEMPLATE.md`. Required: Summary, Type of change and evidence, Runtime evidence, Results, Risk.
- At most 400 changed lines (`make pr-gates`); the `diff-limit-exempt` label skips the limit and needs a justification.
- A PR that changes results or settles a design choice adds a record under `decisions/` (see `decisions/README.md`).
- A build change (`Makefile`, `configure`) changes documentation in the same PR (`make pr-gates`).

### Branch model

- Trunk-based on `master`; feature branches `<type>/<short-slug>`; squash merge.
- Branch protection on `master`: require the `All checks passed` check (see Enforcement Index; not applied yet).
- A branch may be deleted only when no open PR bases on it. Land dependent PRs sequentially. Rewriting pushed history only with `--force-with-lease`.

### Coverage threshold

- Target 80% line coverage of `src/`. Temporary until the target is reached: the floor is the frozen value in `constraints.yaml` (`baseline.coverage_percent`), which may only rise.
- Read an uncovered line as a dead-code candidate first and a missing test second.

## Code Review Self-Check

- Can explain "why this approach" vs the nearest obvious alternative; matched existing patterns unless there is a stated reason to diverge.
- Verified the bug/feature is addressed at the correct layer (not just silencing a symptom).
- Ran the checks selected per `### Scoped verification` and they pass on this branch.
- Added/updated tests for the change, and verified they fail before the fix and pass after (where the change type requires it).
- Checked for canonicality violations: no `_v2` files, no duplicated logic, no dead functions, no scratch dirs.
- No new hidden state: nothing in the right-hand side depends on anything but `(t, y)` and the frozen step inputs.
- Kept the diff focused: no drive-by refactors, no unrelated formatting churn.
- PR description states intent, approach, test plan and risk, and says what was **not** tested.

## Agent Operating Rules

### What agents may do

- Commit to feature branches; open PRs targeting `master`.
- Run builds, gates and example runs locally.
- Propose updates to `AGENTS.md` (human review before merge).

### What agents may not do

- Push directly to `master` or force-push to any shared branch.
- Use `--no-verify` to skip hooks.
- Modify CI workflow files or `tools/ci/` without flagging it in the PR description.
- Relax a threshold, tolerance or baseline in `constraints.yaml` to make a change pass.

### Out-of-bounds operations

- Reproducibility flags: do not change or bypass `-O2 -ffp-contract=off -fno-fast-math`, and do not introduce fast-math options, unless the PR exists for that purpose and a human approved it.
- Reference results: `tests/reference/` and the comparison tolerances change only for a physical reason, with a before/after comparison in the PR; CI never writes reference results.
- User-facing formats: input formats, output file names and binary layout, command-line options, and the run-log lines external scripts read, do not change without approval.

### Attribution, skills, memory

- Agent-authored commits end with `Co-authored-by: <agent name> <noreply address>`.
- Repo skill: `.claude/skills/pre-push-checks/SKILL.md` — follow it before pushing or claiming checks pass.
- Per-session scratch files go in a temporary directory outside the repo, never in the working tree.

### Debugging CI failures (protocol)

1. Identify the failing job: `static`, `build-test`, `secrets` (`.github/workflows/ci.yml`).
2. Read the log; extract the first `FAIL [gate]` line and the exact `make` command.
3. Reproduce locally with the same command. Fix the root cause, not the symptom.
4. Re-run that gate, then push. A platform-only failure needs proof: command, exit code, the platform difference.

### Evidence requirements

- Success claims require fresh command output from the current session: command + exit code + relevant output.
- **Verify the world, not the self-report.** Re-run the command, re-read the file, compare the output files; do not cite your own earlier summary.
- Every comparison of results states all four: commit, build variant, SUNDIALS build, configuration.
- When a claim implies "and nothing else changed", assert it (other output files byte-identical).
- PRs include a `## Runtime evidence` section; "None — review-only change" is allowed only with a stated reason.

### Scoped verification — evidence matches the surface

| Change surface | Narrowest evidence |
|---|---|
| Model source (`src/`) | `make lint`, `make test`, `make regress` |
| Gate tooling (`tools/ci/`, `constraints.yaml`) | `make test-guardrails`, plus the gate that changed |
| Docs | `make docs-check` |
| Build (`Makefile`, `configure`) | `make shud`, `make shud_omp`, `make regress` |

- Report only commands actually run. Full `make ci` is for a repo-wide change, an explicit request, or CI diagnosis.
- Derive the change list from an explicit base: `git diff --name-only <base>...HEAD`.

### Iteration loop gates

- Max 3 fix-and-recheck cycles per failing check; then stop and report what was tried.
- Never weaken, skip, or delete a test to get green.
- One task = one branch; parallel agents use separate git worktrees.

- `tests/reference/` and `tests/io_contract/` are changed only through `UPDATE=1`, reviewed hunk by hunk; `tools/ci/baseline/*.txt` entries are only removed or lowered, together with the counts in `constraints.yaml`.

### Incident-to-constraint ratchet

- An escaped defect that was subtle, systemic and costly gets a write-up under `decisions/postmortem/`.
- A non-obvious lesson costing more than 30 minutes becomes a dated entry in `## Important Development Notes`.
- The third same-class incident becomes a gate in `tools/ci/` — stop writing prose, write the check.

### Known blind spots (handed to review)

- Coverage gate: proves lines ran, not that results are right — review checks test strength.
- Regression gate: one small case, 3 days; no lake, no trapezoidal channel, no frozen soil. It detects change, not physical correctness.
- Bit-identity holds only with the SUNDIALS built by `./configure`.
- Dead-code gate: fails on new findings only; entries that became stale are not reported (cppcheck versions differ).
- Naming gate: file and directory names only, not identifiers.
- Branch protection is not applied: until an admin applies it, a failing CI does not block a merge.
